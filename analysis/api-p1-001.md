## Summary

P1-001 adds two related capabilities to `simple-email-gw`:

1. A new MCP tool, `append_email`, that performs a pure IMAP `APPEND` of an RFC822 message to a folder.
2. Optional auto-save support in `send_email` and `reply_email` so that a successfully sent message is appended to the account's Sent folder.

The design keeps SMTP and IMAP clients decoupled while still allowing the MCP layer to orchestrate cross-cutting "send then save" behavior. Auto-append is non-blocking for the send result: if SMTP succeeds but IMAP append fails, the operation still returns success with a warning.

## Key Design Decisions

### 1. Pure `append_email` tool transports a raw RFC822 message

The new tool is a thin wrapper around IMAP `APPEND`. It accepts a base64-encoded RFC822 message rather than reconstructing fields, because:
- It avoids duplicating the MIME construction logic already in `SMTPClient`.
- It preserves all headers exactly as generated, including `Message-ID`, `References`, and `In-Reply-To`.
- It is genuinely "pure IMAP APPEND" and can be reused for any message source.

### 2. Auto-append is implemented in `SMTPClient` with an injected `IMAPClient`

`SMTPClient.send_email` and `reply_email` gain `append_to_sent` and `append_folder` parameters plus an optional `imap_client`. When auto-append is requested, the SMTP client serializes the MIME message it just sent and delegates the append to the injected IMAP client. This keeps the orchestration at the service layer while letting the MCP tool use a single call.

### 3. Sent folder discovery uses IMAP special-use `\Sent`

`IMAPClient` exposes `find_sent_folder()` which scans the result of `list_folders()` for a folder whose flags contain `\Sent`. If no special-use flag is advertised, the method falls back to common names (`Sent`, `Sent Items`, `Sent Messages`) in a documented, deterministic order. Callers decide what to do when no Sent folder is found.

### 4. Message-ID is generated before SMTP submission

`SMTPClient` currently does not add a `Message-ID`. P1-001 should add one before calling `_send()` so the appended copy is identical to the transmitted copy and threading headers remain stable.

### 5. Append failure must not fail the send

The contract is: SMTP send is the primary operation; IMAP append is a best-effort side effect. If send succeeds but append fails, the response includes `appended: false` and `append_warning`, but the HTTP/MCP call returns success. This matches acceptance criterion #6.

## Error Handling Contract

| Scenario | Status Code / Tool Result | Response Body |
|----------|---------------------------|---------------|
| SMTP send succeeds, append succeeds | 200 / success | `{status: "sent", appended: true, append_folder: "Sent", append_warning: null}` |
| SMTP send succeeds, append fails | 200 / success | `{status: "sent", appended: false, append_folder: null, append_warning: "..."}` |
| SMTP send fails | 500 / ToolError | Existing error behavior |
| Append folder not found | 200 / success (send side) | `append_warning: "Sent folder not found"` |
| Invalid append folder name | ToolError / ValueError | Existing validation behavior |
| IMAP rate limit during append | 200 / success (send side) | `append_warning: "Rate limit exceeded..."` |

All append warnings should also be emitted via the audit logger at warning level.

## Authentication & Authorization

- No new authentication scheme is introduced.
- Auto-append requires both SMTP and IMAP credentials from the same `EmailAccount`, which the connection pool already enforces.
- Audit logging should record both the SMTP send and the IMAP append attempts.

## MIME and Threading Header Preservation

1. Before SMTP submission, `SMTPClient` generates a stable `Message-ID` using `email.utils.make_msgid()`.
2. `In-Reply-To` and `References` are sanitized by existing helpers and stored in the same MIME object.
3. The exact byte serialization used for SMTP is captured with `msg.as_bytes()` and reused for IMAP append.
4. Because the same bytes are appended, all headers, content types, boundaries, and encoding are preserved.

## Implementation Sketch

### `IMAPClient.append_email`

```python
async def append_email(
    self,
    folder: str,
    message: bytes | email.message.Message,
    flags: list[str] | None = None,
) -> dict[str, str]:
    safe_folder = sanitize_folder_name(folder)
    message_bytes = message.as_bytes() if isinstance(message, email.message.Message) else message
    flag_str = "(" + " ".join(flags or []) + ")" if flags else "()"

    async with self._operation_lock:
        client = await self.connect()
        status, data = await client.append(safe_folder, flag_str, message_bytes)
        if status != "OK":
            error_text = _decode_error(data)
            raise RuntimeError(f"Failed to append message: {error_text}")
        return {"status": "appended", "folder": safe_folder}
```

### `IMAPClient.find_sent_folder`

```python
async def find_sent_folder(self) -> str | None:
    folders = await self.list_folders()
    sent_flags = {"\\SENT", "\\Sent"}
    for folder in folders:
        flags = {f.upper() for f in folder.get("flags", [])}
        if flags & sent_flags:
            return folder["name"]

    candidates = ["Sent", "Sent Items", "Sent Messages"]
    names = {folder["name"] for folder in folders}
    for candidate in candidates:
        if candidate in names:
            return candidate
    return None
```

### `SMTPClient.send_email` append path

## OpenAPI Considerations

This task targets MCP tools rather than HTTP endpoints. The tool signatures above serve the same contract purpose. If an HTTP API is added later, the same resource-oriented principles apply:
- `POST /accounts/{account}/folders/{folder}/messages` for append.
- `POST /accounts/{account}/outbox` for send with optional `save_to_sent` field.
